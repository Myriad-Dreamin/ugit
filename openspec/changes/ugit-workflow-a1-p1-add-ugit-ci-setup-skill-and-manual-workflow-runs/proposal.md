Implement one end-to-end proposal: a repo-local ugit CI setup skill plus CLI, server, and web UI support for manual workflow execution, status tracking, and log inspection. This proposal is one candidate implementation for the request: We would like to add a codex skill to help setup ugit ci script for repositories. With the skill, users can interact with codex to create CI script and triggers CI job on the remote server. this call `ugit workflow run [workflow]` to trigger CI job. A workflow id is generated and we can watch the streaming CI logs using `ugit workflow logs [workflowId]`. Users can also see the list and status of triggered workflows in web UI. ugit is git service running on your remote machine. - git remote set to ssh URL of ugit server - use `ugit` command to create a PR. - the repository is synced using git - when receving a PR via http, ugit starts a process to run CI and then merge the PR if CI is successful. ugit will run each `.ugit/workflows/[workflow]/` (A NPM package) to validate. queue CI job at the commit in the remote server. can run one CI job on each remote repository at the same time. at most 4 CI jobs can be run at the same time in the remote server. remote server will checkout the branch and run CI job, and then push the result to the remote repository. the result is stored in `.data/ci-results/[repo-name]/[branch-name].json`. - all of the network communication is done via ssh or http over ssh Initialize a CLI using clipanion, located in `/packages/ugit-cli/src/main.ts`: - the config is stored in `~/.local/share/ugit/config.json` and contains: ```jsonc { "machines": { "local": { // specially treated as localhost rather than a remote machine, so that the remote url is `/path/to/ugit/server/.data/repos` instead of `ssh://kamiya-machine-x/absolute/path/to/repo.git` "ssh-machine": "localhost", "path": "/path/to/ugit/server", "serverPort": 3001 } "machine-x": { "ssh-machine": "kamiya-machine-x", "path": "/path/to/ugit/server", "serverPort": 3001 } } } ``` - setup a local repository in the remote ugit server: ```bash ugit create -m machine-x [directory (default: current directory)] ``` A remote repository is initialized in `.data/repos/[repo-name]`, and the origin of the local repository is set to the ssh URL of the remote repository. the local repository must have a upstream remote, which will be copied to the remote repository as `upstream` remote (assumed being a github URL). ugit push to the remote repository will be synced to the remote repository. This also writes a git local config to record which machine the repository is connected to, so that we can use `ugit` command in the repository without specifying the machine name. - forward a remote server port to local: ```bash ugit serve -m machine-x [-p local-port (default: same as serverPort in config)] ``` - publish PR using the CLI: ```ts export type GitPlatformPublishedBranch = { repositoryPath: string; branchName: string; commitHash: string; remoteName?: string; }; ``` - synchronize PR using the CLI: ```ts export type SynchronizeGitPlatformPullRequestArgs = { repositoryPath: string; branchName: string; baseBranch: string; title: string; body: string; draft?: boolean; remoteName?: string; }; ```.

- Planner deliverable: Proposal: `Add ugit CI setup skill and manual workflow runs` Suggested OpenSpec change: `workflow-skill-a1-p1-add-ugit-ci-setup-skill` Why one proposal: - The Codex skill is not independently useful without a stable `ugit workflow run` / `ugit workflow logs` contract and a server-side workflow-run model to execute against. - The CLI, remote queueing, log streaming, and web UI all need the same workflow-run identity and status model. Splitting them would create partial behavior that pooled coding lanes could not validate end-to-end. Repository context: - `packages/ugit-cli` already has Clipanion wiring, machine config loading, machine inference, `ugit create`, `ugit serve`, and PR commands over HTTP-over-SSH. - The server already has SQLite-backed CI queueing, detached worktree execution, workflow package discovery under `.ugit/workflows/*`, and artifact writing for PR-triggered jobs. - The web app currently lists repositories and repository root entries only; it does not expose workflow history or log views. - `.codex/skills` currently only contains OpenSpec skills, so the requested CI setup skill will be a new repo-local skill surface. Implementation objective: - Add a repo-local Codex skill that can inspect a repository, create or update `.ugit/workflows/<workflow>/` as an npm package with a `ugit:ci` script, explain prerequisites, and optionally trigger and inspect that workflow through ugit CLI commands. - Extend the CLI with `ugit workflow run <workflow>` and `ugit workflow logs <workflowId>` using the existing machine inference and HTTP-over-SSH transport patterns. - Add server-side manual workflow-run APIs, durable workflow-run storage, shared queue coordination, and streaming log delivery. - Expose workflow run history and status in the existing Next.js web UI for each repository. - Validate with `pnpm fmt`, `pnpm fmt:check`, `pnpm lint`, `pnpm test`, and `pnpm build`. Expected implementation shape: - Reuse current repository and machine resolution. `ugit workflow run` should likely push the current branch HEAD to `origin` before queueing the run so the remote server has the commit to execute. - Treat manual workflow runs as the same CI resource class as PR-triggered jobs, sharing the existing one-active-per-repository and four-active-globally limits instead of creating a second independent runner. - Introduce durable workflow-run records keyed by workflow ID, storing repository, branch, commit, workflow name, status, timestamps, and any result/log paths. Persist live logs in a tailed file or equivalent append-only store that both CLI and web UI can read. - Add Next.js API routes for starting a workflow, listing workflow runs, fetching run status, and streaming or tailing logs. The CLI should consume the same HTTP-over-SSH endpoints that the browser uses after `ugit serve`. - Extend the repository page with a workflow history panel and add a dedicated run detail view if needed for clean status and log presentation. - Create `.codex/skills/ugit-ci-setup/` with `SKILL.md` plus minimal references/templates for common workflow packages. The skill should inspect the repository before generating files and fail clearly when the repository is not yet connected to ugit. - Add focused tests around CLI parsing/output, push-before-run behavior, queue sharing, log streaming, API validation, and UI rendering of workflow histories/statuses. Update `README.md` with manual workflow and skill usage. Scope boundaries: - No GitHub Actions or third-party CI integration. - No browser-based workflow editor; authoring remains local through Codex skill plus filesystem changes. - No expansion beyond the current conservative CI capacity rules unless a later proposal changes them. - No redesign of PR auto-merge beyond queue integration required so manual runs and PR runs share capacity safely. Assumptions and risks: - This proposal assumes `ugit workflow run` should operate on the current branch HEAD after pushing it to ugit `origin`. If arbitrary commit selection or no-push behavior is required, the contract should be revised before approval. - This proposal assumes manual workflow runs share queue capacity with PR-driven CI. If they are meant to be isolated, storage and scheduling need replanning. - Streaming logs require a long-lived Node process and persisted log output that can be tailed by both CLI and web UI; a serverless deployment model would change the implementation shape. - The request only requires list/status visibility in the web UI. Detailed in-browser live log streaming can remain follow-up scope if tighter initial scope is preferred, but the underlying log API still needs to exist for `ugit workflow logs`.
