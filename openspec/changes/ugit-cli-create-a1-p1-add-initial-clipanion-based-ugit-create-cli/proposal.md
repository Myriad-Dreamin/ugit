This proposal is one candidate implementation for the request: We have a plan as follow, lets propose to update readme and create a CLI that only implements `ugit create -m machine-x`. ugit is git service running on your remote machine. - git remote set to ssh URL of ugit server - use `ugit` command to create a PR. - the repository is synced using git - when receving a PR via http, ugit starts a process to run CI and then merge the PR if CI is successful. ugit will run each `.ugit/workflows/[workflow]/` (A NPM package) to validate. queue CI job at the commit in the remote server. can run one CI job on each remote repository at the same time. at most 4 CI jobs can be run at the same time in the remote server. remote server will checkout the branch and run CI job, and then push the result to the remote repository. the result is stored in `.data/ci-results/[repo-name]/[branch-name].json`. - all of the network communication is done via ssh or http over ssh Initialize a CLI using clipanion, located in `/packages/ugit-cli/src/main.ts`: - the config is stored in `~/.local/share/ugit/config.json` and contains: ```jsonc { "machines": { "local": { // specially treated as localhost rather than a remote machine, so that the remote url is `/path/to/ugit/server/.data/repos` instead of `ssh://kamiya-machine-x/absolute/path/to/repo.git` "ssh-machine": "localhost", "path": "/path/to/ugit/server", "serverPort": 3001 } "machine-x": { "ssh-machine": "kamiya-machine-x", "path": "/path/to/ugit/server", "serverPort": 3001 } } } ``` - setup a local repository in the remote ugit server: ```bash ugit create -m machine-x [directory (default: current directory)] ``` A remote repository is initialized in `.data/repos/[repo-name]`, and the origin of the local repository is set to the ssh URL of the remote repository. the local repository must have a upstream remote, which will be copied to the remote repository as `upstream` remote (assumed being a github URL). ugit push to the remote repository will be synced to the remote repository. This also writes a git local config to record which machine the repository is connected to, so that we can use `ugit` command in the repository without specifying the machine name. - forward a remote server port to local: ```bash ugit serve -m machine-x [-p local-port (default: same as serverPort in config)] ``` - publish PR using the CLI: ```ts export type GitPlatformPublishedBranch = { repositoryPath: string; branchName: string; commitHash: string; remoteName?: string; pushedAt?: string; }; ``` - synchronize PR using the CLI: ```ts export type SynchronizeGitPlatformPullRequestArgs = { repositoryPath: string; branchName: string; baseBranch: string; title: string; body: string; draft?: boolean; remoteName?: string; }; ```.

Implementation objective: - Add `packages/ugit-cli` with Clipanion entrypoint `packages/ugit-cli/src/main.ts` and implement only `ugit create -m <machine> [directory]`. - Create the initial root README to explain ugit, the config file shape, prerequisites for `ugit create`, and planned future commands that remain out of scope. - Leave `ugit serve`, PR publish/synchronize, CI queueing, merge automation, and `.data/ci-results` handling for later proposals. Expected implementation shape: - Add `pnpm-workspace.yaml` and adjust root scripts as needed so the existing validation commands cover the new CLI package too. - Add a config loader for `~/.local/share/ugit/config.json`, including the `local`/`localhost` special case for filesystem paths versus SSH URLs. - Implement `ugit create` to default to the current directory, require an existing local git repository, require a local `upstream` remote, derive the repo name from the directory name, create the remote repo under `<machine.path>/.data/repos/<repo-name>`, configure the remote repo `upstream`, set local `origin`, and write the selected machine into local git config for future ugit commands. - Add focused tests for config parsing, machine resolution, remote URL/path generation, local git preconditions, and child-process orchestration with mocks. Scope boundaries: - No `serve` command. - No PR publication/synchronization implementation. - No CI runner, merge queue, or HTTP endpoint work. - No behavioral changes to the existing Next.js app beyond workspace/bootstrap adjustments needed to host the CLI package. Assumptions and risks: - The request mentions both `.data/repos/<repo-name>` and an example SSH URL ending in `.git`. Because the current repo already models working-tree repositories under `.data/repos/<repo-name>`, this proposal assumes the first `create` flow targets that working-tree path directly. A bare-repo-plus-checkout model should be treated as follow-up scope if desired. - Safe first-cut behavior should fail with actionable errors for missing `upstream`, unknown machines, remote path collisions, or conflicting existing `origin` remotes instead of mutating silently. - `pnpm build` currently runs only `next build`; approved implementation should expand build orchestration so the CLI package is validated too.
