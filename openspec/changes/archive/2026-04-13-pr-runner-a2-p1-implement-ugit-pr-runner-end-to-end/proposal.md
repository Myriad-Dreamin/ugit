This proposal is one candidate implementation for the request: We have a plan as follow, lets create a PR runner satisfying requirements. ugit is git service running on your remote machine. - git remote set to ssh URL of ugit server - use `ugit` command to create a PR. - the repository is synced using git - when receving a PR via http, ugit starts a process to run CI and then merge the PR if CI is successful. ugit will run each `.ugit/workflows/[workflow]/` (A NPM package) to validate. queue CI job at the commit in the remote server. can run one CI job on each remote repository at the same time. at most 4 CI jobs can be run at the same time in the remote server. remote server will checkout the branch and run CI job, and then push the result to the remote repository. the result is stored in `.data/ci-results/[repo-name]/[branch-name].json`. - all of the network communication is done via ssh or http over ssh Initialize a CLI using clipanion, located in `/packages/ugit-cli/src/main.ts`: - the config is stored in `~/.local/share/ugit/config.json` and contains: ```jsonc { "machines": { "local": { // specially treated as localhost rather than a remote machine, so that the remote url is `/path/to/ugit/server/.data/repos` instead of `ssh://kamiya-machine-x/absolute/path/to/repo.git` "ssh-machine": "localhost", "path": "/path/to/ugit/server", "serverPort": 3001 } "machine-x": { "ssh-machine": "kamiya-machine-x", "path": "/path/to/ugit/server", "serverPort": 3001 } } } ``` - setup a local repository in the remote ugit server: ```bash ugit create -m machine-x [directory (default: current directory)] ``` A remote repository is initialized in `.data/repos/[repo-name]`, and the origin of the local repository is set to the ssh URL of the remote repository. the local repository must have a upstream remote, which will be copied to the remote repository as `upstream` remote (assumed being a github URL). ugit push to the remote repository will be synced to the remote repository. Implementation objective: - Materialize one change that extends the CLI with machine inference, `ugit serve`, and PR publication/synchronization helpers based on the provided `GitPlatformPublishedBranch` and `SynchronizeGitPlatformPullRequestArgs` shapes; add a server-side PR intake API reachable through HTTP over SSH; persist PR/job state durably; run remote CI jobs with one active job per repository and four globally; execute `.ugit/workflows/*` packages against the queued commit; write `.data/ci-results/<repo>/<branch>.json`; and fast-forward merge green pull requests into their base branches. Expected implementation shape: - Reuse the existing machine config and `ugit.machine` git-local setting so commands can infer the target machine inside an initialized repository while still allowing `-m` overrides. - Add a shared SSH/HTTP transport helper in `packages/ugit-cli` that powers both `ugit serve -m <machine> [-p <local-port>]` and the PR synchronization flow. `ugit serve` should establish an SSH local port forward to the remote Next.js server; local machines should short-circuit without SSH. - Add a PR-facing CLI command, likely under `ugit pr ...`, that publishes the branch to the ugit `origin`, captures the published-branch metadata, sends the synchronize payload to the remote server, and prints the queued CI state. Keep the provided TypeScript shapes as the shared contract even if the command surface wraps them. - Keep `ugit create` behavior intact except for extracting reusable helpers needed by the new commands. - Add server-side route handlers/modules for pull-request synchronization. They should validate the request, resolve the target repository under `.data/repos`, persist PR/job records durably, and trigger or nudge the background runner without requiring direct network protocols beyond SSH and HTTP-over-SSH. - Use durable job state for queue coordination, preferably on top of the existing server-only SQLite layer, while still writing final CI result artifacts exactly to `.data/ci-results/<repo>/<branch>.json`. - Run CI from isolated temporary git worktrees or equivalent detached checkouts rooted from the remote repository so queued jobs do not mutate the live receive-updated working tree while pushes continue. - Enforce the scheduling limits explicitly: at most one active CI job per remote repository and at most four active jobs across the whole server. The runner should leave queued work persisted so it can resume safely after a process restart. - Define one explicit workflow execution contract for `.ugit/workflows/<workflow>/` packages in this change, document it, and treat missing scripts or install failures as CI failures with actionable result output instead of silent skips. - After all workflows pass, attempt an automated merge back into the base branch on the remote repository using one conservative strategy, preferably fast-forward-only, and persist merge success or failure in the CI result. - Add focused Vitest coverage around machine inference, port-forward command building, PR request validation, queue coordination limits, result artifact writing, workflow discovery/execution orchestration, and merge success/failure cases. Update `README.md` to document the new commands and operational contract. Validation contract: - `pnpm fmt` - `pnpm fmt:check` - `pnpm lint` - `pnpm test` - `pnpm build` Scope boundaries: - No GitHub/GitLab API integration; the `upstream` remote remains informational and copied through the existing `create` flow. - No redesign of the existing `ugit create` repository bootstrap beyond helper extraction needed for shared transport and machine resolution. - No web UI for reviewing PRs or CI history unless a minimal HTTP endpoint is required for the CLI contract. - No concurrency beyond the requested per-repository and global CI limits. - No automatic conflict resolution or alternate merge strategies beyond the chosen conservative merge rule. Assumptions and risks: - The request says each workflow is "a NPM package" but does not define which script to execute. If deployment is serverless-like, the owner will need to approve a different runner host shape. - Fast-forward-only auto-merge is the safest default for the first cut, but it means base-branch drift or non-ancestor histories will end as non-merged CI results instead of implicit merge commits. - Because `.data/repos/<repo>` is a receive-updated working tree, running CI directly in place is unsafe; isolated worktrees are required for correctness.
